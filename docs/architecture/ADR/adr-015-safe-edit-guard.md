# ADR-015: Safe-Edit Guard - PreToolUse Hook, Skills, and Layered Defense

| Field | Value |
|---|---|
| **Status** | Accepted (v0.8); amended for #159 (tiered rules) |
| **Date** | 2026-05-31 |
| **Deciders** | Alper Hankendi |
| **Decision** | Ship a PreToolUse hook (`ctxo gate-hook`) that blocks edits to high-impact symbols until the agent has called `get_blast_radius`, plus three model-invoked skills (`ctxo-understand`, `ctxo-safe-edit`, `ctxo-review-pr`) installed by `ctxo init`. Claude Code gets full hook enforcement; Cursor gets skills and rules only. |
| **Relates to** | Epic 7, [ADR-012](adr-012-plugin-architecture-and-monorepo.md) |

---

## Context

The fundamental problem: a permanent solution to "the agent forgets" cannot rely on the agent remembering.

Ctxo exposes 14 MCP tools. `get_blast_radius` is the most critical - it shows what breaks before the agent touches anything. But an agent that has access to the tool can still skip it. Rules and prompts reduce skip rates; they do not eliminate them. The agent reads the rule file at session start, navigates to a target file, spots the function, and edits it - skipping the blast radius check because the local context made the edit seem small.

The failure mode is invisible. There is no error. The edit lands. Dependents break. The agent, not having checked, does not know to fix them.

### Why rules alone are not enough

Rules are guidance. They work when the agent is oriented and unhurried. They fail when the agent is mid-task, context is deep, and the edit feels routine. Three observations from real sessions:

1. Agents follow rules at task start. They stop following them mid-task.
2. The symbols most likely to be skipped are the ones that look small but are high-dependency (utility functions, interfaces, base classes).
3. No rule can interpose between the agent's decision and the Edit call.

### Cursor's limitation

Cursor (through v3.6) has no blocking pre-edit hook mechanism. It has rules and prompts but no equivalent of Claude Code's `PreToolUse` hook. Any gate on Cursor is advisory. This is a platform constraint, not a design choice, and it is documented honestly in the platform matrix.

---

## Decision

### Layered defense

Three layers work together, each compensating for the one above:

| Layer | Mechanism | Enforces? | Platforms |
|---|---|---|---|
| Rules | AI rule files generated by `ctxo init`: compact for Claude Code with the guard and skills, full elsewhere | No | All |
| Skills | Model-invoked markdown in `.claude/skills/` and `.cursor/rules/` | No | Claude Code, Cursor |
| Hook | `ctxo gate-hook` registered as PreToolUse in `.claude/settings.json` | Yes | Claude Code only |

Rules reach every platform. Skills provide structured, named instructions the model can reference by name (invoke skill `ctxo-safe-edit`). The hook is the only layer that actually blocks.

### Gate decision

A symbol is flagged as high-impact if it clears both thresholds:

- **Blast radius**: confirmed + likely dependents >= `minDependents` floor
- **PageRank percentile**: symbol falls in the top N% of the codebase by centrality

Both checks must pass. A popular-but-isolated symbol (many importers, no real call chain) does not trigger the gate. An isolated god node with deep calls but no imports does not trigger the gate. Both signals are required to reduce noise.

The thresholds are repo-relative, not fixed numbers. This keeps the guard calibrated across projects of different sizes.

Sensitivity levels:

| Level | PageRank percentile | Min dependents floor |
|---|---|---|
| `strict` | top 30% | 2 |
| `balanced` (default) | top 15% | 3 |
| `lenient` | top 5% | 5 |

### Hook behavior

- **Fail-open**: if `ctxo gate-hook` errors, crashes, or times out, the edit proceeds. The guard is a safety net, not a hard dependency. An unreachable index does not block work.
- **Block-once per session**: once an agent has called `get_blast_radius` for a symbol in a session, subsequent edits to that symbol pass through immediately. No repeated interruptions for the same symbol.
- **Zero false positives for small symbols**: symbols below the thresholds are never blocked. The majority of edits in any session go through without the hook firing.
- **Matcher `Edit` only**: `ctxo init` registers the hook with matcher `Edit`, and `ctxo gate-hook` ignores every other tool. `Write` (new files and whole-file rewrites) and `NotebookEdit` are not gated; `MultiEdit` no longer exists in Claude Code.

### Skills

Three skills installed to `.claude/skills/<name>/SKILL.md` (Claude Code) and `.cursor/rules/<name>.mdc` (Cursor):

- `ctxo-understand` - orient with `get_context_for_task` at the start of a task, and pick the right tool for a structural question (reading a file to see its contents needs no index call)
- `ctxo-safe-edit` - run `get_blast_radius` and `get_why_context` before any edit
- `ctxo-review-pr` - run `get_pr_impact` before reviewing a diff

Skills are passive markdown. They do not execute code. Their value is naming: the agent can invoke a skill by name rather than re-deriving the tool sequence each time. The hook is what enforces.

### New CLI commands

- `ctxo blast-radius <symbolId> --json` - compute blast radius for one symbol, JSON to stdout. For CI scripts, jq pipelines, and pre-merge checks.
- `ctxo gate --preview [--json]` - show which symbols the current sensitivity would flag. For tuning before committing to a sensitivity level.

## Consequences

### Positive

- Edits to high-impact symbols are provably preceded by a blast radius check on Claude Code.
- The check fires exactly once per symbol per session - low friction for compliant agents.
- Skills give Cursor users structured guidance even without enforcement.
- `ctxo gate --preview` makes sensitivity tuning observable before it takes effect.
- Fail-open design means the guard never blocks legitimate work if the index is unavailable.

### Negative / Accepted trade-offs

- Claude Code only for enforcement. Cursor and other platforms get skills and rules only. This is a platform constraint with no workaround until those platforms ship pre-edit hooks.
- The guard does not cover renames, deletes, or batch edits via non-Edit tools unless those are also routed through the PreToolUse hook. Scope is Edit calls.
- Session state is a file store, not process memory. `ctxo gate-hook` runs as a new process per Edit call, records the symbols it already warned about in `.ctxo/.cache/gate/<session_id>.json`, and also accepts a `get_blast_radius` call found in the session transcript. The state survives MCP server restarts; each session writes its own file, so no locking is needed.

### Deferred

- **Layer-3 UserPromptSubmit nudge** - a prompt-level reminder when the guard has been active. Deferred: hook enforcement already covers the case; nudges risk prompt noise.
- **Cursor reactive stop-hook gate** - blocked on Cursor shipping a pre-edit extension point. Revisit when/if that changes.
- **Tier-3 platform enforcement** - Windsurf, Copilot, and others. Same dependency on platform hooks.
- **Adoption telemetry** - track how often the gate fires, is satisfied, and is bypassed. Gate on confirmed user demand.

---

## Alternatives considered

### Rules only

Guidance in `CLAUDE.md` and `.cursor/rules/ctxo.mdc`. Already implemented. Insufficient alone - see Context above.

### Periodic reminder hooks

Use `PostToolUse` or session-start hooks to nudge the agent after an edit if it skipped blast radius. Rejected: the harm has already occurred by the time the post-edit hook fires. Prevention is better than remediation.

### Block all edits until blast radius is checked

Block every Edit call regardless of symbol impact score. Rejected: creates constant friction for routine edits on small symbols. The per-session, high-impact-only design is intentional to keep the guard from becoming an annoyance that users disable on day two.

### Shared session state via external store

Persist the checked-symbol set across server restarts via SQLite or a file. Adopted in a minimal form: per-session JSON files under `.ctxo/.cache/gate/`. A shared SQLite store was not needed.

## Amendment: tiered rules (#159)

### Context

The full rules block is 33 lines, and Claude Code loads it into every session. Its first sentence told the agent to call ctxo before reading any source file, which costs a tool call where none is needed. On Claude Code the guard and the skills already carry the procedure, so the always-loaded text can shrink to a pointer at them. The rules writer also had two defects: files written in create mode (`.cursor/rules/ctxo.mdc`, `AGENTS.md` and the rest) were overwritten whole, and a new `CLAUDE.md` got no markers, so the next run appended a second block.

### Decision

**Two tiers.**

- **Compact** (6 non-blank lines: both markers, the `## ctxo` heading and three lines of text; the cap is 8 non-blank lines including the markers, because Prettier's layout puts a blank line around each marker and after the heading): the repo has a ctxo index, use the ctxo tools for structural questions before grepping, a pre-edit guard blocks the first edit to a high-impact symbol until `get_blast_radius` has been called for it, and the names of the three skills. Written into `CLAUDE.md` only when the guard hook is registered (in `.claude/settings.json`, or in `.claude/settings.local.json`, which ctxo reads but never writes), all three skills are in `.claude/skills/`, and `gate.enabled` is not `false`.
- **Full**: every other client, Claude Code whenever one of those three is missing, and a rules file that several clients share (an `AGENTS.md` or `GEMINI.md` that is a hard link or a symlink to `CLAUDE.md`, detected by real path and by device and inode). Its first sentence is narrowed to "For structural questions (dependencies, impact, history), use ctxo tools first; reading a file to see its contents needs no index call." Step 3 reads "Only then edit the source", and the em dashes are gone. The heading is unchanged, so the tier can be read from the first non-blank line.

The tier follows the disk, not the flags. `ctxo init` resolves it after its skills and guard steps (a dry run counts what it would install as present), so `--no-guard` or `--skip skills` gives Claude Code the full block when the guard or a skill is not already installed; neither flag removes anything.

**Versioned markers, replaced in place.** The block sits between `<!-- ctxo-rules-start v<version> -->` and `<!-- ctxo-rules-end -->`. The version is `RULES_TEMPLATE_VERSION`, the template version: the CLI minor in which the template text last changed. It is hand-set, not read from `package.json`, so a release that leaves the template alone does not mark every committed block outdated. Every platform file is written the same way:

- The first ctxo block is replaced in place: a versioned block, an unversioned `<!-- ctxo-rules-start -->` block, or the pre-marker body older versions wrote (matched with formatting ignored). Later blocks collapse into the first one, and the text between them is kept.
- Every byte outside the blocks is kept, and so are the file's UTF-8 BOM and line endings. A file without a block gets one appended. A new Cursor file gets frontmatter, and the old frontmatter is replaced.
- Three cases leave the file unchanged with a warning: a start marker without an end marker, an end marker without a start marker, and a block from a newer template (a teammate upgraded first). Two tier-aware CLIs (0.13 and later) in one team therefore never flip the block back and forth. A pre-0.13 CLI does not read the versioned marker: it can still append a second block or rewrite a create-mode file whole, and it rewrites the skills, so a team upgrades together.

**Formatter-stable text, normalised comparison.** Both bodies and the bundled skills are written in the layout Prettier prints (a blank line around each marker and after each heading, a padded table), and a test runs Prettier over each and expects identical bytes. Blocks, legacy bodies and skills are compared after a normalisation that drops what a formatter changes: the BOM, line endings, trailing whitespace, blank lines and table padding. The equality test for blocks and skills also treats every whitespace run as one space, so prose that a `proseWrap: always` or `never` setting re-wrapped is not an edit. A block that differs from the template only in these ways is current and is not rewritten, and the tier is read from the first non-blank line, so a formatted compact block is not mistaken for an opt-out. ctxo and a formatter therefore never rewrite each other's output.

**Versioned skills.** Each bundled `SKILL.md` ends with `<!-- ctxo-skill v<version> -->`. `SKILLS_TEMPLATE_VERSION`, next to `RULES_TEMPLATE_VERSION` and with the same meaning, is the CLI minor in which the skills last changed. An installed skill with a newer marker is left alone with a warning, and doctor does not call it outdated; one with no marker or an older marker is outdated and replaced. The marker had to ship with the first tier-aware release: a later one could not teach a 0.13 CLI to leave a newer skill alone.

**Granular init.** `ctxo init` runs its parts in one order: `config` (`.ctxo/config.yaml`, the `.gitignore` entry, `.ctxo/index/`), `skills`, `guard`, `rules`, `mcp`, `git-hooks`. `--only <parts>` installs exactly those, `--skip <parts>` everything else, and `--no-guard` never installs the guard; it combines with both. `--only` cannot be combined with `--skip` or `--rules`, and an unknown part exits 1. `--rules` becomes a deprecated alias for `--skip git-hooks,guard` and prints a notice. The language-plugin step is not a part: `--only` and `--rules` skip it, `--skip` keeps it. Interactive init asks the guard question only when Claude Code is selected, and not at all with `--no-guard`. No config is written for an opt-out: a versioned full block in `CLAUDE.md` records that the user declined the guard and the skills, and `gate.enabled: false` that they declined the guard.

**One rule against a silent opt-out.** Because a versioned full block records an opt-out, no writer may turn a block that expects the guard and the skills into one behind the user's back. One helper, `rulesHold`, decides it for init (the real run, the dry run, `--only rules` and `--rules`) and for `doctor --fix`. It holds the Claude Code or Cursor rules file unchanged when all of these hold: its block is pre-tier or compact; the user has not declined the pieces (`--no-guard`, the guard question answered no, or `gate.enabled: false` for the guard; `--skip skills` for the skills; leaving a part out with `--only` or `--skip guard` is not declining); and after the run's skills and guard steps the pieces still are not on disk (an unreadable `.claude/settings.json` counts as no guard, and a skill counts only when its file is readable and current, the same test the tier uses). Init prints `<file>: left unchanged until the guard and skills are installed; run "ctxo init --only rules,skills,guard" or "ctxo doctor --fix"`, and the dry run reports `unchanged (held)`. A rules file linked to a held one is held too, so a write under the other name cannot reach the held block. A file without a ctxo block is never held.

**Doctor checks.** Three checks report drift as a warning and never fail:

- `ai_rules` (AI rules): a block that is outdated (unversioned, an older template, or the current version with an edited body), a Claude Code block that expects the guard while it is missing, a current block in the wrong tier, several blocks in one file, a start marker without an end marker, or an end marker without a start marker. A block from a newer ctxo passes. Linked files are reported once, under the first name.
- `skills` (Agent skills): missing or outdated ctxo skills for Claude Code and Cursor, where they are expected (one ctxo skill is already installed, or the platform's block is pre-tier or compact). A copy that differs only in formatting is current, and a skill from a newer ctxo is not reported.
- `claude_guard_hook` (Claude guard hook): a `.claude/settings.json` that cannot be read safely (invalid JSON, JSONC comments, or an unexpected shape), or a missing guard while the `CLAUDE.md` block expects it (pre-tier or compact) and the gate is enabled.

A versioned full block and `gate.enabled: false` pass as opt-outs. `ctxo doctor --fix` runs Config, Git hooks, Skills, Claude guard hook and then AI rules, which re-renders the blocks whenever any of the three checks warned, so the tier follows what the same run installed. It installs nothing the user declined and never writes an unreadable `.claude/settings.json`. It holds a rules block by the same `rulesHold` rule as init, whatever stopped the pieces (an unreadable settings file, a failed install): rendering then would write a versioned full block, which reads as an opt-out the user never made. The hold is reported, and doctor keeps reporting the missing pieces until they are fixed. `--fix` replaces an edited ctxo skill with the bundled copy, so a customised skill belongs under another name.

**Tool-selection guide in `ctxo-understand`.** The compact block names the skills instead of listing tools, so `ctxo-understand` carries a question-to-tool table that covers all 14 tools. Its description no longer tells the agent to call ctxo before reading source, to match the narrowed wording.

### Consequences

- With the guard and the skills installed, a Claude Code session loads 4 lines of ctxo rules text (6 non-blank lines with the markers) instead of the full guide. The procedure lives in the skills, and the guard enforces the part that matters most.
- Re-running `ctxo init` or `ctxo doctor --fix` is idempotent: one block per file, user content kept, `unchanged` when nothing changed, a formatter's reshaping included.
- Unmarked pre-tier bodies are recognised with formatting ignored. A body whose words were edited is not found, and the next run appends a second block next to it.
- A rules file shared by several clients never gets the compact block. Its versioned full block reads as an opt-out, so doctor does not report a missing guard there; init's defaults still install the guard and the skills.
- A pre-tier or compact block can stay as it is for a while: it is held until the user installs the guard and the skills or declines them.
- Cursor gets the skills and the full block, but no guard question and no hook.
- The CLI tarball size limit was raised from 1450 KB to 1650 KB (measured 1574.88 KB with the final fix), per the established practice of raising it with the measured size when a PR crosses it, and then to 2000 KB by the owner ahead of the stack merge with PR 1B (about 1870 KB together; 1587.18 KB for this PR alone). Sourcemaps keep shipping.
